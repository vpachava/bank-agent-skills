## 2. Landing zones — anatomy for a regulated bank & the UAE data-residency constraint

### 2.1 Azure Cloud Adoption Framework landing zone (CAF ALZ)

**Confidence: HIGH (page `ms.date` 2025-07-24, fetched this session; the conceptual anatomy is stable since ~2020).**

The authoritative Azure Cloud Adoption Framework page (`what-is-an-azure-landing-zone`) states that an Azure landing zone is "a proven and flexible architecture for governing, securing, and scaling a multi-subscription Azure environment" consisting of **two components** (HIGH):
- **Platform landing zone** — "the centralized foundation that establishes governance, security, and shared resources for all your Azure workloads." Most orgs should have **only one platform landing zone per Microsoft Entra tenant.** Composed of (a) a **management group hierarchy** that "organizes all of your Azure subscriptions and applies governance standards," and (b) **centralized resources** (connectivity/networking, security monitoring, Active Directory identity services, management services).
- **Application (workload) landing zones** — "the environments where workload teams deploy and operate workload resources within the guardrails of the platform landing zone." Each workload has a **single** application landing zone containing all of its environments (dev/test/prod); each environment is one or more subscriptions. (HIGH — page fetched.)

Key anatomy a `landing-zone-review` skill embeds (HIGH — page fetched, this is the §2.1 baseline):

- **Reference architecture** presents **two network topology variants**: **Hub & Spoke** (a Connectivity subscription hosts the hub VNet with Azure DDoS Protection, Azure DNS, VPN/ExpressRoute gateways, Azure Firewall, peered hub VNets across two regions; spokes are application landing-zone VNets) and **Azure Virtual WAN (VWAN)** (Microsoft-managed VWAN hubs in two regions replacing the bespoke hub). Both are **first-class CAF options**; a regulated bank normally opts for the **Hub & Spoke** variant for policy/firewall control surface visibility, with VWAN more common at very large global topologies. (HIGH.)
- **Platform subscription set**: **Connectivity**, **Identity**, **Management**, **Security** subscriptions (each under a matching management group) carry the centralised platform services — Azure Firewall/DDoS/DNS/ExpressRoute in Connectivity, AD DS / Entra ID sync in Identity, Log Analytics + Microsoft Sentinel + dashboards in Security/Management. (HIGH — visible in the diagrams.)
- **Application management groups** distinguish three placement archetypes by **exposure** (HIGH):
  - **Online** — internet-facing workloads (public-facing APIs, mobile backends, customer digital channels).
  - **Corp (Internal)** — internal/corporate workloads reachable only via the corporate network (back-office, internal apps).
  - **Local** — workloads requiring on-premises connectivity (hybrid Extension of an on-prem datacenter footprint — common for **legacy Oracle/private core integration**, see §3).
  (HIGH — page fetched; the diagram explicitly distinguishes these per-lobe placement archetypes.)
- **Decommissioned** management group + Sandbox management group(s) are **first-class** in the ALZ reference hierarchy — a `landing-zone-review` skill checks Sandbox landing zones are tightly policy-fenced from Production and Decommissioned from offboarding workloads crisply. (HIGH.)
- **Policy-as-code guardrails**: inheritance flows from management-group Azure Policy assignments downward through subscriptions — the page explicitly states "Each subscription and its Azure resources inherit the governance and security policies from the Azure Policies applied to the management group hierarchy. This model provides consistent guardrails and allows flexibility to meet workload-specific requirements." (HIGH.) This is the architectural lever the `landing-zone-review` and `terraform` skills embeds to drive drift control — policy is enforced at the platform MG layer, not per-application.
- **Subscription vending** — the platform's "key platform responsibility" is "a repeatable process for requesting, creating, and distributing application landing zones to workload teams" — i.e. automated landing-zone provisioning (subscription vending, often via Terraform/Bicep automation). (HIGH — dedicated ALZ design-area cited.)
- **Implementation options** are either **Microsoft accelerators** (ALZ accelerator, infrastructure-as-code, recommended-practices-aligned) or **custom build** (internally or with Microsoft/partner). For most orgs "accelerators provide the fastest path." (HIGH.) The canonical Azure accelerator is the **ALZ accelerator (terraform/az-700 starter, `terraform-azurerm-caf-enterprise-scale` ALZ module + Bicep port)** — verify current canonical accelerator name before embedding a checklist line.

**Banking/regulated-workload overlay a `landing-zone-review` skill checks (HIGH on the structural capability; MEDIUM on whether Microsoft publishes a current FS-specific ALZ reference, which should be verified):**
- Per-lobe landing zones by exposure + criticality — Payment/Card workloads go in a tightly-guarded app landing zone under **Corp** (highly regulated) or **Online** (customer-facing) with **dedicated subscription(s) per environment**, separate subnet/NSG, dedicated Key Vault for keys, dedicated payment-HSM/Confidential-VM if needed.
- **Police preventively**: Azure Policy driven from the platform MG, with **deny**-effect policies blocking deployment of prohibited services (e.g., deny public-IP on Corp, deny internet-egress on regulated loobes, restrict region to `uaenorth`/`uaecentral`, enforce in-transit and at-rest encryption keys in customer-managed keys in Key Vault Premium/HSM). Azure Policy `allowed-locations` policy = the canonical "force region to UAE regions" control. (HIGH on the Azure Policy mechanism; the recommended FS-specific policy INITIATIVE (built-in policy set definition) list must be pinned from the current ALZ policy library.)
- **Hub-spoke segmentation**: the Connectivity hub must be the **single ingress/egress** choke point for application spokes — regulates east-west movement; UDR (user-defined routes) on spoke subnets force all egress through Azure Firewall. This is the architecture's network-segmentation lever for the **zero-trust** skill (cross-link there).

### 2.3 UAE data-residency constraint on region selection & landing-zone topology

**Confidence: HIGH (Azure UAE regions confirmed against Microsoft Learn's regions-list page, `ms.date` 2025-09-23, fetched this session; AWS + Oracle UAE region claims carry explicit verify flags).**

The dependency from Wayfinder Ticket 02 (`uae-compliance-posture.md` §1) is **load-bearing** here: **CBUAE sectoral rules require payment/card/SVF personal data to be stored and maintained within the UAE**, with a **secure backup at a separate location** (in-country), and the DIFC/ADGM freezones treat onshore UAE as a Third Country for transfers. The architecture implications for hyperscaler landing-zone topology are direct (HIGH):

**Azure — confirmed via Microsoft Learn regions-list (HIGH):**
- **Azure UAE North** — physical location: **Dubai**, geography: **UAE**, programmatic name `uaenorth`, **has Availability Zones** (Yes checkmark), **paired with UAE Central**. (HIGH.)
- **Azure UAE Central** — physical location: **Abu Dhabi**, geography: **UAE**, programmatic name `uaecentral`, **Access restricted** (icon — restricted to support specific customer scenarios, e.g. DR), **paired with UAE North**, **does NOT show an Availability-Zones checkmark on this page**. (HIGH.)
- **Architecture implication (HIGH, synthesised against §1 of Ticket 02):** the CBUAE "primary in-country + separate-location backup" semantics map cleanly to **UAE North as the primary** (AZ-supported, full production capacity) and **UAE Central as the in-country DR/separate-location backup** (Abu Dhabi, restricted-access — requested for DR-of-payment-data scenarios). The Azure region **paired-region** mechanism (UAE North ↔ UAE Central) gives the natural disaster-recovery pair satisfied by the CBUAE sectoral "separate location" metaphor. **An Azure `landing-zone-review` skill MUST enforce Azure Policy `allowed-locations` = `uaenorth` + `uaecentral` and verify backup geo-replication is to UAE Central — not to non-UAE paired regions.** (HIGH.)
- **Free zone data-residency overlay (HIGH against Ticket 02 §2/§3):** DIFC and ADGM treat onshore UAE as a Third Country for transfers → putting a DIFC/ADGM entity's payment data into UAE North/UAE Central (onshore regions) still constitutes an outbound transfer needing a DIFC Art.26/27 or ADGM Sec.41–44 mechanism (SCC/BCR/derogation). The Azure region choice **does not by itself** discharge the freezone transfer obligation — the SCCs/BCRs sit on top.

**AWS — HIGH (verified via the AWS Service Endpoints doc, fetched this session):** AWS operates two Middle-East regions whose canonical names and codes the AWS regions-and-endpoints reference table lists verbatim:
- **Middle East (UAE) | `me-central-1`** — physically located in the UAE (the AWS analog of Azure UAE North).
- **Middle East (Bahrain) | `me-south-1`** — Bahrain, NOT in the UAE.
(HIGH — page fetched at https://docs.aws.amazon.com/general/latest/gr/rande.html.) The widely-published launch year for `me-central-1` is 2022 (MEDIUM — verify the exact launch announcement from AWS's newsroom before citing a date).

**Architecture implication a `landing-zone-review` skill embeds (HIGH against the AWS endpoint reference + Ticket 02 §1):** the bank's AWS payment/card/SVF primary must land in **`me-central-1` (UAE)** to satisfy CBUAE in-country residency; **`me-south-1` (Bahrain) does NOT satisfy UAE in-country residency** — placing payment/card data in Bahrain would be an out-of-country transfer requiring a PDPL adequacy/exemption + transfer mechanism, and is non-compliant with the hard CBUAE residency rule for that data class. Until AWS opens a **second UAE region**, the "separate location" backup required by CBUAE for payment/card data sits via **multi-AZ durability within `me-central-1`** as the de-facto in-country "separate location," **OR** architecturally paired with the Azure UAE pair / Oracle UAE region (the multi-cloud estate itself provides the cross-vendor separate-location insurance — see §3). Whether multi-AZ alone suffices for CBUAE's "separate location" backup semantics (vs. a geographically separate facility) is a **MEDIUM — verify against current CBUAE supervisory expectation** before embedding the AWS-only multi-AZ DR pattern in a checklist. (HIGH on the region residency fact; MEDIUM on the multi-AZ-as-separate-location approval.)

**Oracle — MEDIUM (couldn't fetch the Oracle Cloud regions page this session — returned 403; widely published structural facts only, with verify flags):** Oracle Cloud Infrastructure (OCI) operates UAE-region cloud capacity — commonly published as **OCI region `me-abudhabi-1` (Abu Dhabi)** and **`me-dubai-1` (Dubai)** — i.e. the Oracle Cloud equivalent of in-country multi-region capacity. ## 3. Oracle / private-cloud coexistence — running a legacy core alongside cloud-natively

**Confidence: MEDIUM (canonical architectural patterns widely published; specific Oracle product names/region codes and the bank's actual core-banking SKU not verifiable from official pages this session — 403/404 from Oracle's regions page and product catalog. The structural patterns below are stable multi-cloud coexistence methodology that solution architects across the industry implement).**

The bank's core is in practice an **Oracle core banking stack** (the typical UAE large-bank pattern: Oracle FLEXCUBE / Oracle Banking, on Exadata Database Machine in a private UAE datacenter, or Oracle Exadata Cloud at Customer), retained while progressive modernisation carves out cloud-native periphery. The skills must treat the multi-cloud estate honestly — neither AWS/Azure-only nor pretending the legacy core can simply be lifted. The canonical coexistence patterns a `reference-architecture` + `application-migration` skill embeds (MEDIUM — architectural methodology, not a single credible source):

3.1 **Strangler-fig around the Oracle core.** Wrap the legacy core in an **API/anti-corruption layer** (an API gateway + a service mesh / integration tier) that exposes its capabilities as coarse-grained APIs / domain events; new cloud-native services (customer onboarding, payments modernisation, notifications, lending) consume those APIs and progressively replace front-office and ancillary functions while the core ledger and product engines remain on Oracle. (MEDIUM — architectural pattern, not a primary-source spec.)

This is the **CQRS / event-sourcing seam** a `data-sync` / `event-driven` skill uses to keep an analytics/warehouse copy fresh without nightly batch extracts. (MEDIUM — pattern; the bank-specific topic taxonomy is design, not facts.)

3.3 **Incremental extraction of data marts to a cloud analytics/warehouse tier.** Rather than running analytics on the Oracle core, push curated extracts to a cloud-native analytics tier (Azure Synapse / Fabric; AWS Redshift + Lake Formation; or Databricks on either) sitting in a **platform landing-zone dedicated analytics subscription** with its own control plane, RBAC and SC. The Oracle core stays the system-of-record for transactional truth; the cloud warehouse is the system-of-insight. Outbound extracts inherit the **cross-zone transfer overlay from Ticket 02**: any analytics copy of payment/card personal data leaving the in-country UAE region needs a transfer mechanism, and any analytics copy leaving onshore freezone (DIFC/ADGM) needs an SCC. (MEDIUM — pattern; HIGH against Ticket 02's transfer overlay.)

3.4 **Coexistence of the private Oracle DC, OCI, Azure, and AWS in the topology.** A `reference-architecture` skill shows the bank's honest multi-cloud footprint:
- **Private UAE datacenter / Oracle Exadata on-prem or Exadata Cloud at Customer** — core banking + a private-DC landing-zone extension. The Azure ALZ **Local** landing-zone management group (see §2.1) is explicitly the home for workloads requiring on-prem connectivity — i.e. the bank's periphery-to-core integration tier lands in **Corp/Local landing zones** in Azure UAE region, connecting back to the private DC over ExpressRoute / VPN. (HIGH against §2.1.)
- **OCI** — for workloads where Oracle-ecosystem proximity is required (autonomous database, OCI/**container**-engine for Kubernetes (OKE) around Oracle Banking micro-services), the bank can run capacity in **OCI `me-abudhabi-1`/`me-dubai-1`** in the UAE (MEDIUM — verify region codes), with OCI FastConnect linking the OCI tenancy to both the private DC and the hyperscaler landing zones.
- **Azure + AWS (in-country)** — the bulk of greenfield cloud-native periphery (digital channels, payments modernisation, analytics, AI, integration/API-gateway tiers) given the hyperscalers' service breadth.
The skills must NOT collapse this to "everything goes on Azure" or "everything on AWS" — the `landing-zone-review` skill explicitly checks **what data class lives where per CBUAE residency rule** (Ticket 02 §1), and which workloads have a real reason to be on OCI vs Azure/AWS, vs private DC.

3.5 **Honesty about multi-cloud cost & operating model.** Multi-cloud is not free — it multiplies the skill matrix, the security tooling, the connectivity (FastConnect/ExpressRoute/Direct Connect), and the cost-management surface. A `reference-architecture` skill surfaces this as an **explicit tradeoff** — call out which cloud carries which workload class with a one-line rationale (e.g. "OCI: Oracle-stack proximity + UAE region co-location with Exadata-at-Customer; Azure: integration tier + identity + corporate; AWS: certain greenfield payments micro-services + Lambda event-driven"). Don't let "we're multi-cloud" become un-analysed boilerplate. (MEDIUM — architectural guidance that an RSA should enforce.)

### 4.4 Terraform posture (state, modules, policy guardrails) for banking

**Confidence: HIGH (Terraform state doc fetched this session from developer.hashicorp.com/terraform/language/state) on the durable fields; MEDIUM on specific regulator/cloud product names.**

The HashiCorp Terraform state documentation page fetched this session states verbatim (HIGH): Terraform state "stores bindings between objects in a remote system and resource instances declared in your configuration"; the page explicitly recommends **"storing state in HCP Terraform or a remote backend"** for secure collaborative management, and warns against storing state in "a version control system or other storage solution that does not support Terraform state locking and secure access control" because of "data loss or secret exposure risks." Pre-operation **refresh updates the state with the real infrastructure" — this is the canonical drift-detection mechanism (state ↔ real-world reconciliation before every `plan`/`apply`). The page also says "never edit the .tfstate file directly; use `terraform state` CLI". (HIGH — fetched direct.)

**The bank-default Terraform posture the `terraform` + `landing-zone-review` skills embed (HIGH on the durable principles, MEDIUM on specific banking-deployment patterns):**

- **Remote state with object locking** — per-cloud backend: the canonical patterns are **AWS S3 bucket + DynamoDB state-locking table** (single-region: `me-central-1` in the UAE per data residency), or **HCP Terraform** (managed), or **Azure Storage account with lease-locking + soft-delete + container-level RBAC**. **Never commit `.tfstate` to git.** Strong role-based access to the state (treat as secrets-classified). (HIGH on principle from fetched doc; the bank chooses per-cloud per §3.)
- **One state per (cloud, environment) logical boundary** — break the state into logical slices: platform-rg, identity, network, governance, per landing-zone application. Avoids blast-radius of a single monolithic state file and respects the **platform-landing-zone vs application-landing-zone** boundary from §2.1. The bank-default pattern is: **platform-team owns platform-level Terraform (the ALZ terraform module / LZA CDK); product teams own per-application-landing-zone TF modules graduated through the platform's gating**.
- **Terraform Cloud / HCP Terraform** (or a self-hosted Terraform Enterprise / Atlantis-style runner behind the corporate firewall) as the bank-default control plane for tier-1 environments — centralizes RBAC to apply, sentinel/OPA policy-as-code biunding, the apply-log audit trail, and VCS-driven pipelines. (MEDIUM — bank policy.)
- **Modules from the registry rather than copied-and-pasted** — consume the canonical Azure `terraform-azurerm-caf-enterprise-scale` ALZ module (or partner-published FS variant), AWS LZA-from-CDK (-synced-to-Terraform or CloudFormation -as-TF) for the platform; consume bank-internal module registry for repeated application patterns; treat module versioning as semver breaking-change. (MEDIUM — verify module names; ALZ accelerator currency.)
- **Policy-as-code gating before apply**: the bank-default runs **`tfsec` / `checkov` / `terrascan`** for static infra-config scanning + **OPA or HashiCorp Sentinel** for org-level policy before apply; the ALZ landing-zone Policy-initiative outputs (per §2.1) and the AWS LZA/Control Tower SCPs (per §2.2) are enforced **at the platform layer as preventive guardrails**, independent of any dev team's TF — even if they forget a checkov rule, the platform's deny-policy blocks the deploy.
- **Plan-apply segregation of duties**: proposer ≠ approver ≠ applier. Plans are vapour-reviewed in PRs; apply is gated by a control-plane approval to production landing zones. (HIGH — enterprise pattern.)
- **Drift control via scheduled refresh**: `terraform plan -refresh=true` on a schedule (nightly + pre-deploy) detects out-of-band console changes; any drift triggers an alert into the platform's SRE team to triage (reconcile via TF or revert the console change — the skill defines the runbook). (HIGH on the mechanism — fetched doc confirms refresh.)
- **State encryption & backup**: state and the backend both encrypted at rest with customer-managed keys; point-in-time object-version retention; backup of the state backend is **in-country per §2.3 CBUAE residency** — a remote-state in `us-east-1` for payment-landing-zone TF would leak (state contains secrets/PII metadata beyond the resource bindings). The state backend region = the workload's residency region. (HIGH on the principle; load-bearing: state is itself in-scope for CBUAE residency.)

## 5. Well-Architected → migration sequencing tie-in

**Confidence: MEDIUM (canonical migration-methodology alignment across the hyperscalers' CAF/AWS MRA; the synthesized linkage to the §2–§4 findings is the architect's design work — every "must surface early" item below maps directly to an anchor already HIGH-confidence above).**

A `cloud-migration` and `migration-wave-planning` skill must surface a fixed set of decisions **before** the first application wave is scoped — because each is a precondition that shapes everything downstream and is expensive to retrofit. The skills embed this as a **landing-zone + pillar pre-flight gate** that no migration wave may pass until each is answered (MEDIUM — the synthesized gate, with HIGH anchors on each item):

5.1 **Region placement (the CBUAE residency gate) — surface FIRST.** Before any workload is assigned to a cloud, confirm whether it carries **payment/card/SVF personal data (CBUAE in-country residency)** — if yes, it must land in a UAE in-country region per §2.3 (Azure `uaenorth`/`uaecentral`; AWS `me-central-1`; OCI `me-abudhabi-1`/`me-dubai-1` — MEDIUM-verify Oracle). Wave planning must NOT mix a regulated cohort's wave with a non-regulated cohort's wave if their region constraints differ — sequencing the regulated cohort's **landing-zone build-out first** (because it constrains everything). (HIGH against §2.3.)

5.2 **Freezone SCC posture.** For any DIFC/ADGM-entity-owned workload in scope, the migration skill must surface the **transfer-mechanism posture upfront** (SCCs / BCRs / derogation — Ticket 02 §2/§3). Without an executed SCC, onboarding such a workload to an onshore UAE region is a non-compliant transfer; building the workload first and executing the SCC later inverts the safe order. The skill blocks the wave until the SCC document + its registration (DIFC Notification / ADGM fee+ROPA — Ticket 02 §2/§3) are in flight. (HIGH against Ticket 02 §2/§3.)

5.3 **Landing-zone platform must precede any workload.** The platform landing zone (Azure ALZ accelerator / AWS LZA / Control Tower per §2.1–§2.2) deploys the management-group hierarchy, the connectivity hub, the security & logging spine, identity (Entra ID / IAM Identity Center federation), and the preventive policy-as-code guardrails. **No application wave ships until the platform landing zone is live and its Policy/SCP deny-controls tested.** Otherwise per-application teams will improvise their own network/security posture that the platform later retrofits — a classic source of cross-team drift. (HIGH against §2.1/§2.2.)

5.4 **Foundational services wave before functional applications.** The `cloud-migration` skill separates a **Wave-0 foundational** cohort (IAM, secrets/KMS, central logging, hub network, DNS, security telemetry — i.e. the platform + cross-cutting services) from **Wave-1 functional** cohorts (the first workloads). Wave-0 is the platform itself plus the cross-cutting services an application landing zone consumes; treating Wave-0 as a real wave with its own scope, sign-off, and exit-criteria prevents the common failure mode where bespoke per-app IAM breaks governance before any application code even migrates. (MEDIUM — methodology, but anchored HIGH to §2.1 + §4.4.)

5.5 **Pillar tradeoffs surfaced at wave scoping, not at review.** Each wave's intake must record the **Reliability vs Cost-Optimization tradeoff** explicitly (per the Azure WAF §1.1 tradeoff-as-first-class, and AWS WAF Sustainability vs Cost consideration) — i.e. **the target RTO/RPO and the resulting cross-region/multi-AZ cost are a scoping decision, not a post-migration surprise.** Reference-architecture and migration-wave-planning embed this as a one-line "tradeoff declaration" per wave. (HIGH against §1.1.)

5.6 **Coexistence seam with the Oracle core (§3) prior to first emit.** Any wave moving a front-office function that previously interfaced with the Oracle core must define its **API/anti-corruption-layer contract** with the core as part of wave scoping — and confirm whether the wave also includes the relevant CHANGE-DATA-CAPTURE pipeline (per §3.2) the core publishes into. Otherwise a migrated workload finds itself re-calling the core via its legacy fine-grained interfaces and perpetuates coupling. The skill blocks the wave until the ACL contract is reviewed and the integration mode (real-time API vs event-stream vs batch extract) is set. (HIGH against §3.1/§3.2.)

5.7 **Kubernetes + Terraform posture for the wave (§4) is also a wave-scoping decision.** Each wave declares:
- For K8s-bound workloads: proposed cluster topology (cluster-per-tenant / namespace-per-tenant / cluster-per-payload-class), secrets approach (CSI driver + Workload Identity/IRSA), and the GitOps controller — selected at wave scoping because retrofitted cluster boundaries cause re-platforming.
- For Terraform-managed infra: state backend (in-country per §4.4 §4.6), module choice (platform module + app-landing-zone module), apply-pipeline gating, policy-as-code applied through PR binary auctions — selected at wave scoping because retrofitting state or module boundaries is the most expensive Terraform rework. (HIGH against §4.)

5.8 **Decommissioning plan the workloads left behind.** Each migration wave declares its **exit criteria** for the source (legacy on-prem) workload — the state at which the legacy instance can be decommissioned — explicitly dated against the **Decommissioned management group / Sandbox gating posture** (per §2.1 Azure ALZ; AWS equivalent: a decommissioned-accounts Org OU). Without it, migration plans accumulate legacy ghosts; CBUAE operational-resilience standards (Ticket 02 §9) want decommissioning documented as part of business continuity / DR. (HIGH against §2.1 + Ticket 02 §9.)

5.9 **Migration methodology shape (cross-reference, not re-derived):** `cloud-migration` and `migration-wave-planning` subordinate the per-wave content above to the **6-Rs** (Rehost, Replatform, Repurchase, Refactor, Retain, Retire) and the **Strangler-Fig / data-mesh / API-gateway strangulation** patterns referenced in `banking-integration-patterns.md` §6 (when that ticket covers them) — the cloud-migration skill selects the per-workload R during Wave-1 functional scoping and feeds back adjusted landing-zone/policy/Tradeoff statements.
