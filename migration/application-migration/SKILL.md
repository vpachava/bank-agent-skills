# /application-migration

## When to apply
Use for the application-component level of migration, ensuring that functional banking units map correctly between environments while managing the complexities of interface and dependency stitching.

## Inputs
- **App Inventory** â€” Current runtime, languages, frameworks, secrets-management.
- **Integration Catalogue** â€” API/Event-interfaces exposed/consumed, message formats (e.g., ISO20022).
- **Compliance Constraints** â€” Residency requirements for logging/tracing data generated by the app.

## Process
1. **Define Migration Strategy.** Map the 6Rs strategy ([cloud-migration](../cloud-migration/SKILL.md)) to the application component.
2. **Catalog/Map Integration Seams.** Rigorously trace all in-app/out-app interfaces ([integration-seams](../../modernization/research/integration-seams.md)).
3. **Transition-State Architecture.** Define how the app architecture looks during the migration process (e.g., intermediate Strangler-fig facades/API-gateways).
4. **Resiliency/Security Update.** Modernize the application security components (e.g., replace legacy creds with managed identity/secrets-manager) and tracing/logging for cloud-governance.
5. **Author application-migration runbook.** Detailed steps, packaging, and configuration changes (e.g., k8s manifests, IaaC updates).

## Banking pitfalls
- **Integration seam neglect** â€” Assuming interfaces are "simple HTTP calls" without realizing they depend on proprietary banking adapters (middleware) that don't exist in the new cloud destination.
- **Configuration hard-coding** â€” Hard-coded secrets/credentials/endpoint-configs that are non-portable across environments; must be externalized to IaC/Managed-Secrets.
- **Ignoring "tracing gap"** â€” Application migrated to cloud but log/trace/audit data is missing from the bank's central observability-toolchain, potentially breaking compliance requirements.
- **Partial cutover fragility** â€” Migration creates a distributed system that spans both legacy/cloud; failing to design for latency and failures in that intermediate hybrid-state.

## Bulletproofing against Rationalization
To prevent migration chaos causing downtime, you MUST:

1. **Mandatory Cutover Reversibility:** The migration plan MUST contain a rollback script, with explicitly defined RTO limits for executing it.
2. **Mandatory Dark Launching:** Customer-facing migrations MUST utilize feature flags or traffic shadowing before full cutover.
3. **Data Parity Evidence:** The plan MUST explicitly define how the legacy and new systems will be mathematically reconciled during the transition.

**Violating these rules invalidates the Application Migration plan.**

## Outputs
- **Application migration plan** â€” Phased plan including transition-architecture.
- **Integration interface mapping** â€” Detailed catalog of all app interfaces and modernization requirements.
- **Deployment transition plan** â€” Infrastructure/packaging updates runbook.

## Anti-patterns
- **Attempting "Big Bang" cutovers for large monolithic application portfolios**
  - **Consequence:** High risk of total failure, massive rollbacks, and multi-day business outages when unexpected bugs occur.
  - **Correct Approach:** Use the Strangler Fig pattern or phased canary rollouts to migrate traffic progressively by function or user group.
- **Lifting and shifting legacy tech debt directly into modern cloud platforms**
  - **Consequence:** Cloud hosting costs spiral out of control while performance metrics remain exactly as poor as on-premises.
  - **Correct Approach:** Execute a basic platformization step to containerize and right-size resources prior to or during the migration wave.
- **Failing to secure proper business sign-off on the target state application SLA**
  - **Consequence:** Business users reject the migrated application because it performs slightly differently than the legacy monolith.
  - **Correct Approach:** Align business, IT, and stakeholders on expected target state NFRs before migration begins, using clear baselines.
