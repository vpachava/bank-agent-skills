# /application-migration

## When to apply
Use for the application-component level of migration, ensuring that functional banking units map correctly between environments while managing the complexities of interface and dependency stitching.

## Inputs
- **App Inventory** — Current runtime, languages, frameworks, secrets-management.
- **Integration Catalogue** — API/Event-interfaces exposed/consumed, message formats (e.g., ISO20022).
- **Compliance Constraints** — Residency requirements for logging/tracing data generated by the app.

## Process
1. **Define Migration Strategy.** Map the 6Rs strategy ([cloud-migration](../cloud-migration/SKILL.md)) to the application component.
2. **Catalog/Map Integration Seams.** Rigorously trace all in-app/out-app interfaces ([integration-seams](../../modernization/research/integration-seams.md)).
3. **Transition-State Architecture.** Define how the app architecture looks during the migration process (e.g., intermediate Strangler-fig facades/API-gateways).
4. **Resiliency/Security Update.** Modernize the application security components (e.g., replace legacy creds with managed identity/secrets-manager) and tracing/logging for cloud-governance.
5. **Author application-migration runbook.** Detailed steps, packaging, and configuration changes (e.g., k8s manifests, IaaC updates).

## Banking pitfalls
- **Integration seam neglect** — Assuming interfaces are "simple HTTP calls" without realizing they depend on proprietary banking adapters (middleware) that don't exist in the new cloud destination.
- **Configuration hard-coding** — Hard-coded secrets/credentials/endpoint-configs that are non-portable across environments; must be externalized to IaC/Managed-Secrets.
- **Ignoring "tracing gap"** — Application migrated to cloud but log/trace/audit data is missing from the bank's central observability-toolchain, potentially breaking compliance requirements.
- **Partial cutover fragility** — Migration creates a distributed system that spans both legacy/cloud; failing to design for latency and failures in that intermediate hybrid-state.

## Bulletproofing against Rationalization
To prevent migration chaos causing downtime, you MUST:

1. **Mandatory Cutover Reversibility:** The migration plan MUST contain a rollback script, with explicitly defined RTO limits for executing it.
2. **Mandatory Dark Launching:** Customer-facing migrations MUST utilize feature flags or traffic shadowing before full cutover.
3. **Data Parity Evidence:** The plan MUST explicitly define how the legacy and new systems will be mathematically reconciled during the transition.

**Violating these rules invalidates the Application Migration plan.**

## Outputs
- **Application migration plan** — Phased plan including transition-architecture.
- **Integration interface mapping** — Detailed catalog of all app interfaces and modernization requirements.
- **Deployment transition plan** — Infrastructure/packaging updates runbook.
